# 系统化调试 — 4 阶段根因分析

## 适用场景

任何**故障 / bug / 异常 / 不符合预期**的报告，都先走这个流程。

特别注意：用户说"我猜可能是 X 的问题，你改一下"时，**不要直接信**——很多时候用户的猜测是错的，按猜测改会浪费时间。

## 核心原则

**先理解，再修复**。

调试 = 信息收集 → 假设 → 验证 → 修复
不是 = 看到错误 → 改一行 → 看好了没

## 4 阶段流程（**严格按顺序**）

> **提示**:开始调试前先调用 `todo_write` 工具建立 4 阶段 todo:
> 1. 复现 bug
> 2. 定位代码位置
> 3. 找到根因
> 4. 修复并验证
>
> 每完成一阶段就标记完成。前端会渲染进度,用户随时知道你卡在哪一步。

### 阶段 1：复现（Reproduce）

**目标**：稳定地让 bug 再次出现。

行动：
1. 用 `question` 工具**逐个**询问用户(不要在 chat 里写 "1. 2. 3." 编号让用户文字回答)。对**选项有限**的问题尤其要用 options 按钮:
   - 完整错误消息 / 堆栈(让用户复制原文,用 `question` 的开放输入)
   - 操作步骤(点了哪些按钮 / 跑了什么命令)
   - 期望结果 vs 实际结果
   - **何时开始的** — 用 options:`["昨天还好今天不行", "本周内开始的", "一直都有", "记不清"]`
   - **复现率** — 用 options:`["100% 必现", "偶发", "只在某个机器/环境"]`
2. 自己尝试复现：
   - 跑同样的命令
   - 在代码里加 log 看实际值
3. **写下复现步骤**作为后续验证修复的标准：
   ```
   1. 启动 sidecar: pnpm tauri:dev
   2. 切到 Code 模式
   3. 输入 "ls"
   4. 观察终端输出 → 期望显示文件列表，实际报错 "platform.terminal 未注入"
   ```

**如果无法稳定复现**：先回到用户那里收集更多信息，**不要瞎改**。

### 阶段 2：定位（Localize）

**目标**：把"哪里出错了"从整个项目缩小到 1-3 个可疑函数 / 文件。

行动：
1. 读完整堆栈：从顶向下找**第一个属于本项目的栈帧**
2. 用 `grep` / `glob` 搜关键字（错误消息、变量名）
3. 用 `codebase_search` 做语义搜索(找概念相关代码,不依赖精确字符串)
4. 用 `lsp` 工具找符号定义 / 引用(查"这个函数被哪些地方调用")
5. 在可疑位置加 log（`console.log` / `console.error`），不要改代码逻辑
6. 重新跑，看 log 输出的值是不是符合预期
7. 用二分法：在中间打 log，确认问题在前一半还是后一半

### 阶段 3：根因（Root Cause）

**目标**：找到真正的因，不是表象。

**5 Why** 法：连问 5 次"为什么"，挖到底层原因。

例子：
- **现象**：终端输出空白
- 为什么？→ xterm 没收到数据
- 为什么？→ pty 没启动
- 为什么？→ `platform.terminal` 是 `undefined`
- 为什么？→ 创建 platform 时漏传 terminal 字段
- 为什么？→ NodePlatform.ts 早期实现忘了 terminal，后来加了 ITerminal 接口但没接进去
- **根因**：NodePlatform 适配器没有实现 ITerminal 字段

### 阶段 4：修复 + 验证（Fix & Verify）

**目标**：改最小代码 + 确认 bug 真的没了。

行动：
1. 改动 **尽量小**（只改根因，不顺手重构无关代码）
2. 重新走阶段 1 的复现步骤，验证 bug 消失
3. 跑现有测试 / typecheck / build（防止改坏其他东西）
4. 加一个**回归测试**或日志，避免下次再犯

## 反模式（绝对不要做）

❌ 看到 `null is not a function` 就加 `if (x) x()` 绕过——根因可能是 x 应该被初始化但没有
❌ 看到 stacktrace 就 `try { ... } catch { }` 吞错误——失去诊断能力
❌ 凭"我觉得是 ..."直接改代码——99% 情况你猜错
❌ 一次改 5 个地方然后说"应该好了"——任何一个都没法独立确认有效
❌ 不复现就修复——可能根本没改对地方

## 何时升级 / 寻求帮助

- 卡在阶段 2（定位）超过 30 分钟没进展 → 让用户分享更多上下文
- 阶段 3 的"为什么"问到第 3 层就答不出 → 涉及外部依赖 / 不熟悉的子系统，建议读官方文档或源码
- 复现需要外部资源（特定数据库 / 第三方 API） → 让用户提供测试环境

## 报告模板

调试结束后给用户：

```markdown
## 根因
[一句话讲清真正的原因，附文件:行号]

## 现象 → 根因的链条
现象：xxx
↓ 为什么？
中间原因 1
↓ 为什么？
中间原因 2
↓ 为什么？
**根因**：xxx

## 修复
- 改动文件：`xxx.ts:123`
- 改动内容：[diff 摘要]
- 改动理由：[1 句话]

## 验证
- ✅ 复现步骤 1-3 现在通过
- ✅ `pnpm typecheck` 通过
- ✅ 加了回归测试 `xxx.test.ts:line`
```

## 与其他技能的关系

- 调试结束 → `verification-before-completion` 做最终验收
- 改动较大 → 先 `writing-plans` 写改动计划再动手
