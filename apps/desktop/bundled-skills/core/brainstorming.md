# 头脑风暴 — 需求探讨与规格落地

## 适用场景（务必先读）

当用户的请求满足以下**任一条件**时，**优先调用此技能**而不是直接动手：

1. 需求只有一句话（"做一个登录功能"、"加个搜索"、"修复 bug"）
2. 涉及多个文件 / 多个模块 / 跨层修改
3. 涉及不可逆操作（删数据、迁移、重构）
4. 用户措辞含有"想 / 看看能不能 / 是不是应该"等不确定语气
5. 工时估计 > 30 分钟

## 核心原则

**不要急着写代码**。代码很容易，理解需求才难。

**苏格拉底式追问**：通过 3-7 个有针对性的问题，把模糊需求收敛成可落地的规格。

## 执行流程

### 第 1 步：复述用户需求（确认理解）

用一句话**回译**用户的需求，让用户确认你没理解错。

格式：
> 我理解你的需求是：[一句话总结]。对吗？

### 第 2 步：识别歧义点

至少识别 **3 个**潜在歧义，逐一发问。常见歧义类别：

- **范围**：是这一处改还是全局改？
- **优先级**：性能优先 / 可读性优先 / 兼容性优先？
- **边界条件**：空值 / 异常 / 并发情况怎么处理？
- **目标用户**：谁会用？什么场景？
- **可接受的代价**：能不能破坏 X？需不需要保留 Y？
- **时间窗**：是先打补丁还是彻底重构？

### 第 3 步：逐个发问（用 `question` 工具）

**用 `question` 工具一次只发一个问题**，每个问题**必须**带 3-5 个 `options`(预设选项让用户一键选)，候选实在难穷举时再让用户自由输入。

```json
{
  "tool": "question",
  "question": "关于范围:这次只改 LoginController 单点登录,还是把全栈认证流程都改?",
  "options": [
    "只改 LoginController",
    "全栈认证流程都改",
    "我也不确定,你给个建议"
  ]
}
```

**等用户回答完一个再问下一个**。问题数控制在 **3-7 个**——超过 7 个说明你没分清主次,先问最阻塞的。

**为什么不批量**:批量提问看起来"省往返",但实际:
- 用户对着一长串编号问题容易漏答
- 后面的问题往往依赖前面的答案(比如选了"A 方案",问题 4-5 就不用问)
- 码弦 的 `question` 工具带 options 按钮,一键点选比手打 "1A 2B 3 跳过" 快得多
- 单问交互让 AI 能根据回答**动态调整后续问题**(类似真人对话)

### 第 4 步：输出规格（结构化）

用户回答后，**明确写出规格**：

```markdown
## 规格

**目标**：[一句话]

**范围**：
- 涉及文件：xxx
- 不涉及：xxx（明确划界）

**接受标准**：
- [ ] xxx 能做到 yyy
- [ ] zzz 不会被破坏

**风险**：
- xxx 可能导致 yyy
- 如果出问题，回滚方案是 zzz
```

### 第 5 步：用户确认后再动手

> 以上规格如果没问题，我就开始实施。

## 反模式（不要这样做）

❌ 用户说"加个搜索"，AI 立刻 `glob "**/*.tsx"` 然后开写
❌ 假设用户的"性能"指的是"渲染速度"（可能是接口响应）
❌ 用 chat 文字把 5-6 个问题一次性甩给用户编号回答(应该用 `question` 工具逐个发)
❌ 问超过 7 个问题——超过这个数说明没分清主次,先问最阻塞的
❌ 把规格写得太详细变成项目计划（详细计划用 `writing-plans` 技能）

## 何时**不**用此技能

- 用户明确说"按你的判断做"或"不用问，直接干"
- 一行代码改动（typo、变量重命名）
- 用户已经在前一轮明确给出了规格

## 与其他技能的关系

- 完成本技能 → 可能调用 `writing-plans`（如果范围大）→ 进入实施
- 实施中遇到根因不明 → 调用 `systematic-debugging`
- 实施完成前 → 调用 `verification-before-completion`
