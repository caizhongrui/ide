# 执行计划 — 按步骤稳定推进

## 适用场景

满足**任一**时调用：

1. 用户已经认可一份实施计划，说"开始做"
2. 收到一份多步任务列表（编号清单），准备落地

## 核心原则

**计划的价值在于按它执行**。

执行 = 一步一步、每步独立验证、出问题立即停。

不要"读完计划，然后一气呵成把全部代码写出来再回头"——出问题没法回到上一个干净状态。

## 执行流程

### 第 1 步：用 `plan_exit` 工具呈现计划等待审批

不要把计划塞进 chat text 然后等用户口头说 "好"。码弦 提供 `plan_exit` 工具:调用后会弹窗给用户审批,**审批前 dispatcher 强制冻结所有写入工具(edit / apply_patch / bash 等)**,所以你不会"偷跑"。

```text
调用 plan_exit,payload 例如:

我即将按以下顺序执行:

1. 在 src/foo.ts 新增 parseX 函数
2. 在 src/bar.ts 调用 parseX 替代 inline 逻辑
3. 添加 tests/foo.test.ts 单元测试

每步完成后我会跑 typecheck,确认无误再进入下一步。
```

用户在弹窗点"批准"后,写入工具自动解锁,继续第 2 步。

### 第 2 步：逐步执行（**关键**）

#### 2.0 用 `todo_write` 建立 todo 列表

进入第 2 步前,调用 `todo_write` 工具把计划里的每个步骤建成一条 todo。码弦 前端会渲染 todo 列表,用户可以实时看到进度;执行中每完成一步就再次 `todo_write` 把对应项标为 completed。

#### 2.1 在新一步开始时

明确告诉用户：

> 进入步骤 2：在 src/bar.ts 调用 parseX 替代 inline 逻辑

#### 2.2 改动**最小化**

只改这一步要改的，不顺手改其他东西。即便发现别处有问题，**记下来**留到后面，不打断当前流程。

#### 2.3 每一步结束验证

| 步骤类型 | 验证方法 |
|---|---|
| 修改源码 | `pnpm typecheck` 通过 |
| 改了接口 | 跑现有相关测试 |
| 新增功能 | 跑新加的测试 |
| 修改配置 | 重启 dev server 看启动是否正常 |

**不通过就立即停**，不要带着错误进入下一步。

#### 2.4 报告进度

每步完成报告一行：

```
✅ 步骤 2 完成：
   - 改动：src/bar.ts:45 调用 parseX 替换 inline
   - 验证：typecheck 通过
   下一步：步骤 3 添加测试
```

### 第 3 步：遇到偏差怎么办

执行过程发现计划和现实**不符**时（例如某个文件结构和计划假设的不一样）：

1. **不要硬着头皮按计划做**
2. 立即停下来告诉用户：
   用 `question` 工具呈现选项,让用户一键点选(不要在 chat 里写 "A/B" 让用户文字回答):
   ```json
   {
     "question": "步骤 2 遇到偏差:计划假设 src/bar.ts 里有 inline parseX 逻辑,但实际看到 src/bar.ts:45 调用的是已存在的 utils/parse.ts。怎么处理?",
     "options": [
       "A. 修改 utils/parse.ts 直接增强(更小改动)",
       "B. 按原计划新建 parseX 然后让 utils/parse.ts 调它"
     ],
     "multiple": false
   }
   ```
3. 等用户在按钮上选择,再继续

### 第 4 步：全部完成后总结

走完所有步骤后：

```markdown
## 计划执行完毕

**完成步骤**：3/3
**实际改动**：
- `src/foo.ts` — 新增 parseX
- `src/bar.ts:45` — 替换 inline
- `tests/foo.test.ts` — 5 个新测试

**验证**：
- ✅ typecheck 通过
- ✅ 旧测试 + 新测试全绿（37/37 passed）
- ✅ 手动验证关键场景

**与计划差异**：
- 步骤 2 计划写"修改 line 45-50"，实际只改了 line 45（line 46-50 不需要动）

**遗留**：
- 发现 src/baz.ts 也有类似 inline 逻辑（不在本次范围，建议后续 PR 处理）
```

然后调用 `verification-before-completion` 做最终验证。

## 反模式

❌ 一口气把所有步骤都改完再统一验证——任何一处出错都不知道是哪步引入的
❌ 跳过中间验证，直到最后才发现不行
❌ 计划和现实不符时硬改代码"凑成计划样"——应该停下来问
❌ 每步完成不报告，用户不知道进度
❌ 中途发现"应该再加个步骤"就偷偷塞进去——计划不应该被默默扩展，应该问用户

## 何时**重新写计划**

执行中如果发现：
- 计划假设错了（架构和理解不同）
- 出现了原计划没考虑的依赖
- 某一步代价远超预估

**停止执行**，回到 `writing-plans` 重新规划。损失是当前步骤工作，但避免了基于错误前提继续浪费。

## 与其他技能的关系

- 执行前必有计划 → `writing-plans`
- 每步验证用 → `verification-before-completion`（轻量版本）
- 全部完成后做最终验证 → `verification-before-completion`（完整版）
- 出 bug → `systematic-debugging`
- 准备提交 → `requesting-code-review`
