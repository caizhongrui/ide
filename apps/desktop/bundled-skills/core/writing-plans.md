# 写计划 — 把"做某事"拆成可执行步骤

## 适用场景

满足以下**任一**时调用：

1. 用户说"先出个方案 / 做个计划 / 拆解一下"
3. 任务涉及 ≥ 3 个文件或 ≥ 2 个层
4. 需要新建模块 / 重构 / 迁移
5. brainstorming 结束后规格大于 50 行

## 核心原则

**计划是给执行者（人或 AI）看的工作指令，不是给老板看的 PPT**。

具体到：
- 每一步都能独立验证
- 步骤之间有清晰的依赖
- 风险点提前识别
- 必须包含回滚方案

## 输出格式（严格）

```markdown
# 计划：[一句话目标]

## 1. 背景与目标

**问题**：[用户当前面临什么]
**目标**：[做完后世界变成什么样]
**非目标**：[明确不做哪些事，避免范围蔓延]

## 2. 现状盘点

[列出当前代码 / 数据 / 配置的关键事实，附文件路径和行号]

- `xxx.ts:123` — 当前实现 yyy
- 数据库表 `users` 字段 zzz 当前类型为 ...
- 配置 `.env.PORT=4096`

## 3. 设计要点

[关键决策 + 理由，每条 1-3 句]

- **选 A 不选 B**：因为 ...
- **接口设计**：xxx 函数签名为 ...
- **数据格式**：使用 JSON 而非 protobuf，理由 ...

## 4. 实施步骤

| 步骤 | 文件 | 操作 | 验证方法 |
|---|---|---|---|
| 1 | `src/foo.ts` | 新增函数 `parseX()` | 单元测试 / 手动跑 `bun test foo` |
| 2 | `src/bar.ts:45` | 调用 parseX 替换 inline 逻辑 | 编译通过 + 现有测试通过 |
| 3 | `migrations/0001.sql` | 新增字段 `created_at` | psql 验证表结构 |

**每一步**必须能：
- 独立运行（不依赖未来步骤）
- 有明确的成功/失败判定
- 失败时知道回退点

## 5. 风险与回滚

| 风险 | 概率 | 影响 | 缓解 / 回滚 |
|---|---|---|---|
| 数据迁移失败 | 中 | 高 | 先 dump，失败立即 restore |
| 接口不兼容旧客户端 | 低 | 中 | 加 X-Protocol-Version header 路由分发 |

## 6. 验收清单

完成后必须满足：
- [ ] `pnpm typecheck` 通过
- [ ] `pnpm test` 通过
- [ ] 手动验证 [关键场景 1]
- [ ] 手动验证 [关键场景 2]
- [ ] 文档更新（README 或对应 .md）

## 7. 后续可选优化（不在本次范围）

- xxx
- yyy
```

## 关键原则

### A. 步骤粒度

- **太粗**：「实现登录功能」（不知道从哪下手）
- **太细**：「在第 23 行加一个空格」（汪洋大海）
- **正好**：「在 auth.ts 添加 verifyToken() 函数，输入 JWT 字符串，输出 user_id 或抛 InvalidToken」

### B. 步骤之间的依赖

- 必须**串行**的步骤标号 1, 2, 3
- **可并行**的步骤同标号（1a, 1b）
- 跨步骤共享变量 / 状态要在该步骤说明

### C. 验证方法必须具体

- ❌ "测试通过" → 哪个测试？
- ✅ "运行 `bun test packages/core/src/auth.test.ts`，所有 case 通过"

## 反模式

❌ 计划里写「实现 X 功能」「完善 Y 模块」（动词太虚）
❌ 不写文件路径只写"前端代码"
❌ 不写验证方法（怎么知道做对了？）
❌ 没有回滚方案（出问题怎么办？）
❌ 把"未来可能要做的"全堆进当前计划（应该放第 7 节"后续可选"）

## 与其他技能的关系

- 计划写完后**用 `plan_exit` 工具**呈现计划等待**弹窗审批**(不要把计划塞进 chat text 让用户口头说"OK")。审批前 码弦 dispatcher 强制冻结写入工具,审批后自动解锁,可以直接进入执行。
- 执行用 `executing-plans` 技能（按计划顺序逐步）
- 完成前用 `verification-before-completion` 对照验收清单
